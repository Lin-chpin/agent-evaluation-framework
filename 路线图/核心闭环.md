# 核心闭环

## 职责分工

通用框架负责机制，领域项目负责语义。

| 通用框架 | 领域项目 |
| --- | --- |
| 执行评测、规范 Trace | 测试集与业务真值 |
| 管理候选身份和隔离工作区 | 允许修改的对象与范围 |
| 对比 improvement、regression、holdout | 业务指标与安全规则 |
| 控制预算、停止、接受和回滚 | 人工验收与生产发布权限 |

测试集、评价规则和人工确认共同为改进提供可执行的判定依据。

## 四层架构

- L0 公理层：`EvalCase`、`NormalizedTrace`、候选身份、策略、结果和审计协议。
- L1 积木层：诊断、候选生成、工作区、候选应用、评测、晋级策略和存储。
- L2 流程层：编排一轮或多轮演化，所有失败和预算耗尽都形成明确状态。
- L3 外交层：CLI 和领域适配器传入业务能力，不把业务目录、API 或 Prompt 名写进核心。

## 必须保持的能力

- 诊断保留失败 case、疑似模块、目标对象和修改边界。
- 候选包含基线版本、目标对象、改动类型、产物和预期改善。
- Prompt、Skill、Few-shot、Schema 和代码候选都在隔离环境中验证，生产文件由外部发布流程管理。
- 领域适配器声明影响场景与保护集，框架执行而不猜测业务影响。
- 循环限制轮数、候选数、模型调用数和总耗时，并原子保存状态。
- 候选接受发生在沙箱，staging 和 production 由外部发布流程继续推进。

## Benchmark 原则

参考任务应包含 baseline、已知问题、改进集、回归集、不可见留出集、好坏候选和可核验口径。AI 可以起草数据，但候选生成前必须冻结；关键规则需要人工确认；来源、版本和确认状态必须留档。

这类 Benchmark 用于验证诊断、隔离、复测和门禁机制，业务方可以在此基础上接入自己的业务测试集和评价口径。

## 为什么机制实验使用 14B 模型

模型大小不是框架的核心自变量。`Qwen/Qwen3-14B` 被用于 AI 参与的机制实验，重点观察框架如何处理非法 JSON、无效候选、过拟合和回归等真实运行中会遇到的情况。

较小模型降低重复实验成本，也更容易暴露失败路径，方便验证门禁对模型波动的适应能力。更大模型可以提高有效候选产出率，业务测试集、人工 gold、regression 和 holdout 则继续为质量决策提供依据。

## 验收分层

- 机制验收：合成任务验证诊断、隔离、改进、回归、留出、停止和审计。
- 系统集成验收：`ai-health-assistant` 验证真实 Agent 编排、Trace 和候选切换没有被框架破坏；其 AI 起草 case 不等于真实医疗业务数据。
- 业务效果验收：使用真实业务标准、专家标注、历史 badcase 或线上反馈完成验收。

## 发布定位

当前定位为面向 Agent 与 Skill 持续质量验证的 Beta 框架：

> 在业务方提供测试集、评价规则和改动边界的前提下，为 Agent / Skill 提供受控的自动评测和候选演化能力。

业务接入可以沿着机制验证、系统集成、业务验收和生产验收逐步推进，框架为每个阶段提供运行记录、门禁结果和回滚依据。
