# 并发稳定性

本页验证框架自身的并发安全，为业务接入提供并发执行、共享状态保护和故障恢复依据。

## 已验证能力

- 同一 `loop-id` 和 `run-id` 使用跨进程锁保持单执行者。
- SQLite 使用 WAL 和有限锁等待，重复 `run-id` 不会静默共享记录。
- 实际 case 并发不超过框架配置与 `ProjectAdapter.max_concurrency` 的较小值。
- 在途窗口固定为有效 workers 的两倍，不随数据集规模无限创建 Future。
- 1、8、32 workers 各运行 1000 case，覆盖瞬态失败恢复、永久失败记账和分段恢复。
- 结果记录吞吐量、P95 Agent 延迟、错误率和 Python traced memory 峰值。
- 10 秒短周期 soak 连续运行 51 批、5100 个 case，0 失败，初始和结束线程数均为 1；机器结果见 `evidence/soak-results.json`。
- 多进程 scale-out 参考矩阵覆盖 4 种负载、1/2/4/8/10/12/14/15/16 个 runner 进程和共享 SQLite WAL；112 个总 workers 连续两次通过，120 和 128 个总 workers 出现结果持久化缺失；机器结果见 `docs/生产级并发验收.md`。
- Docker Compose 容器拓扑已完成四类负载验证；8 个 runner 容器 × 8 workers 均通过网络 Agent stub 调用并经 named volume 汇总，单档 2000/2000/2000 结果完整、0 硬失败、24/24 瞬态失败恢复。该证据仍在单一物理主机、每 runner 独立 SQLite 上运行，不等同于多主机或共享生产存储。

当前结果支持“在参考负载和 SLO 下可稳定运行至 112 个总 workers”的判断；120 是共享 SQLite WAL 的压力边界，不纳入稳定支持档位。多主机调度、生产拓扑容量和业务 SLO 仍需在目标部署环境中验证。

## 目标生产拓扑验收（当前主线）

当前已进入目标生产拓扑验收的门禁冻结阶段，但尚未开始 M4 结果判定。目标环境至少需要登记多机或目标集群、runner 调度、网关/队列、共享持久化、真实上游 Agent、业务 SLO、故障注入和回滚负责人。没有这些实际环境证据，单机 Compose 结果不升级为生产声明。
