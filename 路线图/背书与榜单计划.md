# 背书与榜单计划

> 当前主线已切换到 [目标生产拓扑验收](未完成事项.md)。BFCL 只保留为次要的外部接入证据，不作为生产级并发结论的前置条件。

## 目标

为 Agent Evaluation Framework 建立可复现、可解释、能在面试中说明白的外部验证材料。

项目的核心不是训练一个 Agent 去刷榜，而是验证评测框架能不能稳定接入不同 Agent，统一处理 Case、Trace、badcase、回归、并发和失败恢复。

因此，外部 benchmark 主要用来证明两件事：

1. 框架能接入公开任务和真实工具调用场景；
2. 框架产出的结果可复现、可对比、可追溯。

## 总体策略

优先做“公开 benchmark 适配 + 原始证据留存”，暂不以冲击榜单排名为目标。

当前项目已经有一组内部工程证据：

- 52 个自动化测试通过；
- 并发 1、8、32 worker 各执行 1000 个 Case；
- 峰值吞吐约 530 case/s；
- 10 个临时失败全部恢复；
- 5 个永久失败被正确记录；
- Soak 测试累计执行 5100 个 Case，0 失败，线程数没有持续增长。

这些结果用于证明框架本身的执行稳定性。它们基于本地合成数据，不代表真实 LLM API 的生产容量，后续报告必须保留这个边界。

## 优先级

### P0：完善可复现证据

继续保留并完善现有 `BENCHMARK_RESULTS.md` 和 `evidence/` 目录中的结果，记录：

- 代码版本；
- Python、操作系统和运行环境；
- 测试命令；
- 原始 JSON 结果；
- 吞吐、延迟、失败恢复和资源使用；
- 合成数据与真实业务容量的边界。

这部分是当前最可靠的项目背书，不依赖外部榜单是否接受提交。

### P1：BFCL 工具调用适配

BFCL 与本项目的 Case、Trace 和工具调用评测最匹配，优先接入 Berkeley Function Calling Leaderboard 的公开数据。

官方入口：<https://github.com/ShishirPatil/gorilla/tree/main/berkeley-function-call-leaderboard>

#### 阶段 A：零成本链路验证

- 使用少量固定输出或已有结果文件；
- 验证 BFCL 数据转换为项目 Case；
- 验证工具调用转换为统一 Trace；
- 验证成功、参数错误、漏调用和多调用的判定；
- API 成本为 0。

#### 阶段 B：小规模接入验证

- 抽取 100～200 条；
- 优先覆盖 `simple_python`、`multiple`、`parallel`，再加入少量 `multi_turn`；
- 使用便宜模型或本地模型；
- API 预算按 1 美元预留；
- 输出 Case 通过率、工具调用准确率、错误类型和 Trace 样例。

这一步只能称为“BFCL 子集接入验证”，不能称为官方 leaderboard 成绩。BFCL 官方支持按 Case ID 运行和 partial evaluation，但部分结果不等同于完整榜单结果。

#### 阶段 C：形成可写进项目的结果

- 扩大到 500～1000 条；
- 至少重复运行一次，观察结果是否稳定；
- 记录模型版本、提示词版本、运行时间、token、成本和失败 Case；
- API 预算按 1～10 美元预留；
- 生成 `evidence/bfcl-results.json` 或等价原始结果，并在 `BENCHMARK_RESULTS.md` 中写清实验范围。

#### 阶段 D：完整 BFCL 或官方提交

只有在前面链路稳定后再考虑。

- 完整跑法要遵循 BFCL 官方数据、模型配置和评测流程；
- 多轮、记忆和 Web Search 会显著增加调用次数和运行时间；
- Web Search 还可能引入 SerpAPI 或其他搜索服务成本；
- 只有按官方要求完成并提交后，才可以描述为 leaderboard 结果。

阶段 A 已完成：`scripts/verify_bfcl_adapter.py --mode self-check` 验证 JSONL 契约、工具调用规范化、正确调用接受、漏调用/错参数/多调用拒绝和 `NormalizedTrace` 转换。该结果只证明接入链路，不包含模型调用，也不是 BFCL 分数。

### P2：τ-bench 业务 Agent 验证

当项目需要证明业务型 Agent 的多轮交互、用户模拟和工具执行能力时，再接入 τ-bench。

官方入口：<https://github.com/sierra-research/tau2-bench>

它比 BFCL 更接近客服、零售、航空和银行等业务场景，但接入成本更高，放在 BFCL 之后。

### P3：EdgeBench 长周期任务验证

EdgeBench 暂不作为第一选择。

官方入口：<https://github.com/ByteDance-Seed/EdgeBench>

EdgeBench 重点测试 Agent 在 12 小时以上的真实环境任务中持续学习和完成任务的能力，并依赖 SForge 评测环境。它更适合证明某个完整 Agent 的长周期任务能力，不直接代表本项目的评测框架质量。

后续如果要接，目标应当是验证：

- 能否接入长周期任务；
- 能否持续保存完整 Trace；
- 能否定位中间 badcase；
- 能否统计任务进展和失败恢复。

不把“跑过 EdgeBench”直接等同于“项目在 EdgeBench 上取得排名”。

## 成本口径

成本按实际模型和 token 用量重新计算，下面只作为立项预算：

| 阶段 | 规模 | 预计 API 成本 | 说明 |
| --- | ---: | ---: | --- |
| 链路验证 | 20～50 条 | 0 美元 | 使用固定输出或本地模型 |
| BFCL 小规模 | 100～200 条 | 约 0.1～1 美元 | 不跑 Web Search |
| BFCL 中规模 | 500～1000 条 | 约 1～10 美元 | 需要考虑多轮和重试 |
| BFCL 全量 | 全部类别 | 视模型和调用次数而定 | 可能增加搜索服务和运行环境成本 |

如果使用本地开源模型，API 成本为 0，但要记录显卡、模型、并发度和运行时间。

## 结果材料

每次外部 benchmark 验证至少保留：

- 数据集版本和 Case 范围；
- Agent 和模型配置；
- 运行命令和代码版本；
- 原始结果 JSON；
- 通过率、工具调用错误率、多轮成功率；
- p95 延迟、吞吐、失败恢复和成本；
- 已知限制和不能外推的结论。

## 面试口径

> 我没有一开始就追求 EdgeBench 这种大榜单，因为它主要衡量完整 Agent 在超长真实任务里的能力，而我的项目重点是评测基础设施。我的做法是先接入 BFCL 的工具调用数据，把公开任务统一转换成项目内部的 Case 和 Trace，再复用 badcase 分析、回归评测、并发验证和结果留存能力。这样既有外部 benchmark 作为参考，也能证明框架本身的评测链路是可复现的。后续如果需要，再按官方协议做完整提交。
