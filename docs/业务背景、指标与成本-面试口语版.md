# 业务背景、指标与成本

## 面试时可以这样开头

我做的是一个 Agent 变更评测和发布前验证框架。

它解决的事情很实际。一个 Agent 的 Prompt、Skill、规则或者代码改了以后，不能只看几个例子觉得效果变好了，就直接替换线上版本。框架会把新版本放进隔离环境，跑固定测试，比较旧版本和候选版本的结果，再决定接受、拒绝还是回滚。

业务方自己提供 Case、Gold 和评价规则。框架负责执行、比较、记录和留痕，发布权限仍然在业务方手里。

## 为什么不接 LLM 也能运行

这里的关键流程本来就不是靠 LLM 做决定。

接入方只需要提供一个适配器。适配器负责调用自己的 Agent，再把原生结果转换成统一的 Trace。Trace 里可以放最终输出、事件、耗时、路由、关键字段和业务自定义指标。

框架拿到 Trace 后，用确定性规则检查结果。比如某个字段必须等于指定值，输出必须包含某个内容，硬门禁不能失败，或者延迟不能超过阈值。这些规则是普通代码，输入相同就会得到相同结果。

然后框架把 baseline 和 candidate 放到同一套数据上比较。结果写入 SQLite，同时生成 Markdown 和 JSON 报告。人工审核也只是把审核结论写入数据库，不需要模型参与。

所以没有 LLM 时，确定性评测、报告、人工审核、回归检查和候选回滚都可以完整运行。

LLM 只是可选项。它可以帮忙诊断 badcase、提出候选修改，或者辅助选择测试范围。它不能直接绕过硬门禁，也不能自己决定候选能不能发布。

## 业务指标怎么接进来

框架不替业务方发明指标。不同 Agent 的业务目标不一样，指标由接入方提供。

常见指标包括任务成功率、路由准确率、关键字段准确率、报告判断准确率、安全规则通过率、延迟、步骤数、重试次数、告警数量和业务方自定义数值。

这些指标可以放在 Trace 的标准字段或自定义字段里。策略文件再规定它们怎么聚合，以及允许下降多少。候选版本只要破坏了必要指标，就会被拒绝或回滚。

## 三类数据怎么分

在候选演化里，我把测试数据分成三种角色。

`improvement` 是候选要解决的已知问题，可以把它理解成错题集。

`regression` 是以前已经正确的能力，候选不能把它弄坏，可以把它理解成已经掌握的题。

`holdout` 是候选生成时不让它看的留出集，用来检查它有没有只针对已知问题做修改，可以把它理解成模拟考试里的新题。

候选要在 improvement 上变好，同时保护 regression 和 holdout。只修好 improvement，却让 holdout 变差，严格策略下仍然会回滚。

这三类是候选版本比较时的数据角色。项目还有普通自动化测试、smoke、regression、full、并发、容器和持续运行测试，所以不能把它们理解成项目全部测试的名字。

## 成本从哪里来

框架本身不强制调用模型，也不收取运行费用。只跑确定性规则时，主要成本就是机器运行时间和测试数据量。

接入真实 Agent 或 LLM 后，成本主要来自几件事。Case 越多，调用越多。失败重试和一致性检查会增加重复调用。候选演化需要分别测 baseline 和 candidate。自动演化还会增加诊断调用、候选生成调用和多轮尝试。

可以先用一个简单的估算方式。普通评测成本大约等于 Case 数量乘以每条 Case 的 Agent 调用次数。版本演化还要乘上 baseline 和 candidate 的评测次数。自动演化再加上诊断和候选生成调用。

实际费用取决于接入方使用的模型、供应商、价格和测试集规模。框架不会把自己的调用次数冒充成供应商账单。真实模型成本应该通过 Trace 自定义指标记录下来，再放进业务策略里比较。

## 我是怎么控制成本的

第一，测试分级。`release` 可以先跑 regression，再跑 smoke，最后按需要跑 full。前面出现硬失败，后面就不继续消耗完整测试集。

第二，演化有预算。可以限制最大轮数、每轮候选数、Evolver 调用数和最长运行时间。

第三，支持断点续跑。运行结果写入 SQLite，自动演化还会保存 checkpoint。中断后可以跳过已经完成的 Case，避免从头再跑。

第四，限制并发和重复运行。适配器可以声明并发上限，只有真正需要一致性检查的高价值节点才会重复运行。

第五，按 diff 选择测试范围。文档和展示层改动可以先跑 smoke，Prompt、安全规则和质检逻辑改动跑 regression，Agent 核心逻辑和评测结果结构改动再跑 full。

## 面试时怎么收尾

我证明的重点是工程闭环可行。候选可以被隔离，结果可以被重复验证，失败可以被记录，坏候选会被拒绝或回滚，模型生成失败也不会直接污染 baseline。

公开样例和外部参考系统主要使用合成 Case，所以我不会把它说成已经证明了某个具体业务的收益。它证明的是这套评测、演化、审计和回滚机制可以接入 Agent，并且能把发布风险控制在流程里。

## 一段更短的说法

我做的是 Agent 变更的受控评测框架。接入方提供 Agent 调用、Trace、业务 Case 和门禁规则，框架负责跑 baseline 和 candidate，比较 improvement、regression、holdout 三组结果，再决定 accept、reject 或 rollback。

即使不接 LLM，规则评测、报告、人工审核、回归和回滚也能运行。LLM 只负责可选的诊断和候选生成，不能绕过确定性门禁。成本方面，我通过分级测试、调用预算、断点续跑、并发限制和按 diff 选测试集，避免每次改动都跑完整套流程。
