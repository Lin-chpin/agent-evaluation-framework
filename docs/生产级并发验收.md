# 生产级并发验收

## 目的

这份证据把框架并发验证从单线程池扩展到多个独立 runner 进程，并让这些进程同时写入同一个 SQLite WAL 数据库。负载仍然由可复现的合成适配器提供，因此不绑定医疗、客服或代码业务语义。

## 参考运行

```powershell
python scripts/verify_scale_out.py `
  --profiles short_io,long_io,trace_heavy,mixed_io `
  --process-counts 1,2,4,8 `
  --workers 8 `
  --cases-per-process 250 `
  --output evidence/scale-out-results.json
```

机器结果见 [evidence/scale-out-results.json](../evidence/scale-out-results.json)。本次 Windows 11、Python 3.13.5 运行覆盖 4 种负载、1/2/4/8 个 runner 进程、8 workers/进程，最高为 64 个总 workers；16 个拓扑全部通过。

边界复测还覆盖了 80、96、112、120 和 128 个总 workers。112 个总 workers 的四类负载连续两次完整通过；120 个总 workers 的两次完整复测分别在 `mixed_io` 和 `trace_heavy` 出现结果缺失，128 个总 workers 的四类负载中 3 类出现结果缺失。对应证据见 [80](../evidence/scale-out-80-results.json)、[96](../evidence/scale-out-96-results.json)、[112](../evidence/scale-out-112-results.json)、[112 复测](../evidence/scale-out-112-repeat-results.json)、[120](../evidence/scale-out-120-results.json)、[120 复测](../evidence/scale-out-120-repeat-results.json) 和 [128](../evidence/scale-out-128-results.json)。

112 总 worker 的 SLO 验收命令为：

```powershell
python scripts/verify_scale_out.py `
  --profiles short_io,long_io,trace_heavy,mixed_io `
  --process-counts 14 `
  --workers 8 `
  --cases-per-process 250 `
  --max-p95-agent-ms 25 `
  --min-throughput 300 `
  --output evidence/scale-out-112-results.json
```

真实业务适配器可以复用同一入口。每个拓扑会把 case 文件按 runner 进程分片，避免同一拓扑重复调用外部 Agent：

```powershell
python scripts/verify_scale_out.py `
  --adapter path/to/project_adapter.py `
  --cases path/to/cases.jsonl `
  --process-counts 1,2,4,8 `
  --workers 8 `
  --max-p95-agent-ms P95_LIMIT `
  --min-throughput THROUGHPUT_LIMIT `
  --output evidence/scale-out-business.json
```

每个拓扑均满足以下硬条件：

- 所有 case 都有结果，唯一结果数与输入数一致。
- 0 个硬失败。
- 注入的瞬时失败全部经过一次重试恢复。
- 共享数据库中的 run 数和 result 数与预期一致。
- 没有进程超时。

## 项目参考 SLO

- 所有四类负载和验收拓扑的 Agent 延迟 P95 不超过 25 ms。
- 在 112 个总 workers 的验收拓扑中，完成吞吐不低于 300 case/s；低于该档位的探索点不使用这个绝对吞吐门槛。
- 结果完整性必须同时满足：0 丢失、0 重复、0 硬失败，注入的瞬时失败全部恢复。

这些是框架参考容量 SLO，不是任意生产业务的端到端 SLO。当前证据支持的稳定声明档位是 **112 个总 workers**；120 是压力边界，不能作为稳定支持档位。

## Docker Compose 容器拓扑验收

本机可用 Docker Compose 启动多个独立 runner、网络 Agent stub 和汇总器：

```powershell
python scripts/verify_distributed_compose.py `
  --runners 8 `
  --workers 8 `
  --cases-per-runner 250 `
  --profile mixed_io `
  --max-p95-agent-ms 25 `
  --min-throughput 300 `
  --output evidence/distributed-compose-mixed_io-20260918.json
```

Docker Desktop 恢复后，使用真实 Docker Compose 完成了 8 个独立 runner 容器 × 8 workers、网络 Agent stub、collector 和 Docker named volume 的四类负载矩阵。每档 2000 个 case，runner 通过 Compose 服务名访问 stub，结果写入 named volume 后由 collector 汇总并导出。

| 负载 | 总 workers | case / stored / unique | 硬失败 | 注入 / 观测瞬态失败 | P95 Agent 延迟 | 吞吐 | 证据 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| `short_io` | 64 | 2000 / 2000 / 2000 | 0 | 24 / 24 | 1.9285 ms | 1657.49 case/s | [JSON](../evidence/distributed-compose-short_io-20260918.json) |
| `long_io` | 64 | 2000 / 2000 / 2000 | 0 | 24 / 24 | 21.4872 ms | 1671.95 case/s | [JSON](../evidence/distributed-compose-long_io-20260918.json) |
| `trace_heavy` | 64 | 2000 / 2000 / 2000 | 0 | 24 / 24 | 6.2671 ms | 1621.97 case/s | [JSON](../evidence/distributed-compose-trace_heavy-20260918.json) |
| `mixed_io` | 64 | 2000 / 2000 / 2000 | 0 | 24 / 24 | 10.4834 ms | 1598.87 case/s | [JSON](../evidence/distributed-compose-mixed_io-20260918.json) |

四档均为 `status=passed`，满足项目参考 SLO（P95≤25ms、吞吐≥300 case/s、0 丢失、0 重复、0 硬失败、瞬态失败全部恢复）。这证明了当前单机上的容器网络拓扑、独立 runner、结果卷和汇总链路可以工作；它仍不证明多主机、共享生产数据库、真实上游 Agent 或生产业务容量。

## 目标生产拓扑验收（当前主线）

当前阶段为“冻结目标环境与门禁”，不是生产验收已通过。进入 M4 结果判定前，必须补齐以下实际证据：

| 验收项 | 当前状态 |
| --- | --- |
| 多机或目标集群拓扑、runner 调度和资源规格 | 尚未登记 |
| 网关、队列、限流和服务发现 | 尚未在目标环境验证 |
| 共享持久化存储、备份和恢复路径 | 尚未在目标环境验证 |
| 真实上游 Agent、模型/供应商和依赖版本 | 尚未登记 |
| 目标业务 P95/P99、吞吐、错误率、成本和资源 SLO | 尚未由目标负责人冻结 |
| 多小时 soak、限流、超时、依赖失败、进程/节点退出 | 尚未执行 |
| 回滚路径、恢复时间和发布责任人 | 尚未演练 |

本阶段的顺序是：登记目标拓扑与责任人 → 冻结业务容量 SLO → smoke → ramp → steady-state → soak → 故障注入与恢复 → 回滚演练 → 重复运行。只有全部适用门禁通过，才能给出该目标环境的生产容量结论；BFCL 或单机合成压测不能替代这些证据。

## 结论边界

这份结果支持以下表述：

> 在单机多进程 runner、共享 SQLite WAL、给定负载包络和最高 112 个总 workers 的参考环境中，框架满足 P95≤25ms、吞吐≥300 case/s，并保持结果完整、失败可记账、重试可恢复。

这份结果不支持以下表述：

- 任意业务或任意生产拓扑都能达到同一个容量。
- 已完成多主机、队列、网关、共享外部服务和生产集群验收。
- 已经得到业务无关的唯一生产并发上限。

脚本通过 `--max-p95-agent-ms 25 --min-throughput 300` 执行项目参考 SLO 判定；目标部署可以根据实际硬件、外部依赖和业务协议覆盖这两个阈值。

## 生产环境运行

接入真实部署时，使用真实 `ProjectAdapter`、代表性冻结 case、真实 Trace 和目标部署拓扑重跑同一流程，并增加业务方的 P95/P99、错误率、成本、资源和质量门禁。满足全部门禁的最高到达速率或并发配置，才是该部署的生产 N；医疗 Agent 的结果只归属于医疗 Agent 这一个负载包络。

当前项目的业务接入验收边界见 [功能列表/业务接入验收.md](../功能列表/业务接入验收.md)。
