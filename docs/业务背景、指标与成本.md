# 业务背景、指标与运行成本

## 适用场景

本项目主要用于 Agent 和 Skill 上线前的候选版本验证。它也可以接收线上 fresh run、Trace 和人工反馈，把问题带回下一轮评测和演化，但不会自动修改或替换生产版本，发布权限仍由业务方掌握。

框架本身不定义具体业务真值。接入方提供业务 Case、Gold、硬门禁、软质量规则和需要关注的指标，框架负责运行、比较、记录和给出候选版本的 `accept`、`reject` 或 `rollback` 决策。

## 业务指标

指标由领域项目提供，常见的指标包括：

- 任务成功率、路由准确率、关键字段准确率和报告判断准确率。
- 安全规则、内容约束、历史 badcase 和人工 Gold 的通过情况。
- 延迟、步骤数、重试次数、告警数量和业务方自定义数值指标。

版本演化固定比较三组数据：

- `improvement`：候选版本声称要改善的问题。
- `regression`：已经确认、不能再次出现的历史能力。
- `holdout`：候选生成过程没有使用的留出样本。

候选版本需要在 improvement 上达到改善目标，同时保护 regression 和 holdout。通过率下降、硬失败、软告警增加或自定义指标超过策略限制时，候选会被拒绝或回滚。

## 成本从哪里来

框架本身没有强制的模型调用，也不收取运行费用。没有接入 LLM 时，确定性评测、报告、人工审核和回归流程仍然可以运行。

接入真实 Agent 或 LLM 后，主要成本来自：

- Case 数量和每条 Case 的 Agent 调用次数。
- 一致性检查的重复运行和失败重试。
- `evolve` 对 baseline 和 candidate 的重复评测。
- `evolve-auto` 的诊断调用、候选生成调用、候选数量和迭代轮数。

粗略理解，普通评测成本约等于 Case 数量乘以 Agent 调用次数。版本演化还要分别运行 baseline 和 candidate，自动演化还会增加诊断和候选生成调用。实际费用由接入方使用的模型、供应商和测试集决定。

## 已实现的成本控制

### 分级测试和硬失败短路

`release` 支持 `regression`、`smoke` 和可选的 `full` 阶段，按顺序运行。前面的阶段出现硬门禁失败，后续阶段停止，避免在已经不合格的版本上继续消耗完整测试集。

### 演化预算

`evolve-auto` 支持以下预算参数：

- `--max-rounds`：最大演化轮数，默认 3。
- `--max-candidates-per-round`：每轮最大候选数，默认 3。
- `--max-evolver-calls`：诊断器和候选生成器的最大调用数。
- `--max-elapsed-seconds`：最大运行时间。

诊断和候选生成的调用次数会单独记账，解析失败只允许在预算内进行受限重试。

### 断点续跑

运行结果会写入 SQLite，自动演化会写入 `checkpoint.json`。使用相同的 run ID 或 loop ID 加 `--resume`，可以跳过已经完成的 Case，并在条件允许时复用已暂存候选，减少重复调用。

### 并发和重复运行控制

业务适配器可以设置 `max_concurrency`，框架会把实际 workers 限制在适配器允许的范围内，线程池也只保留有限的在途任务。重复运行和一致性检查都有明确边界，只有启用一致性检查的高价值节点才会重复运行。

## 按 diff 自动选测试集的实现状态

当前项目已经实现 `smoke`、`regression`、`full` 的分级执行，以及演化预算和硬失败短路。它还没有内置一个自动读取 Git diff、判断改动影响范围、再自动选择测试集的 selector。

接入方目前可以在 CI 或领域适配层根据改动范围选择测试集。例如，低风险展示改动跑 smoke，生成、RAG 或评测结构改动跑 full，Planner、Prompt、安全规则和质检逻辑改动跑 regression。这个路由规则属于接入层流程，不能在项目介绍中写成当前框架已经自动完成的能力。

## 结论

当前框架已经能限制测试阶段、演化轮数、候选数量、模型调用次数、运行时间、并发压力和重复执行。按 diff 自动选择测试集是一个明确的降本方向，目前仍属于接入层实现或后续功能，不属于现有内置能力。
