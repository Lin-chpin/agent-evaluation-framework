## 高度相似的是失败后的工程流程

相似点不止是双方都能自动跑评测。更接近的部分在于失败之后怎么处理。

两边都沿着这条路走：

```text
发现 Bad Case
    ↓
保留 Case 与 Trace，分析失败原因
    ├── Agent 本身有问题
    │       ↓
    │   修复 Agent → 回测 → 通过门禁后进入发布流程
    │
    └── 评测标准或覆盖范围有问题
            ↓
        修正 Metrics / Rubric / 评测集
            ↓
        用历史样本回归，检查评测体系本身是否可靠
```

美团白皮书明确把 Case 挖掘与归因设为两条 Loop 共用的入口。归因发现 Agent 有问题，就进入 Agent 修复、回测和上线；发现评测集漏掉了问题，就补充样本；发现 Rubric 判断有偏差，就修正评价标准。评测体系的改动也要通过新案例和回测校准。[《Agent评测白皮书》](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html)

我的项目也有这两条演进路径。Agent 候选会进入隔离环境，使用 improvement、regression、holdout 三类数据验证，再由规则决定接受、拒绝或回滚。[自动评测](../../功能列表/自动评测.md)、[受控演化](../../功能列表/受控演化.md)和[评测 Skill 自进化](../../功能列表/评测Skill.md)分别说明了这些流程。

工程分叉也很接近。评测结果若暴露 Agent 问题，改的是 Prompt、Skill、工具策略或代码；若结果暴露评价口径或样本覆盖问题，改的是 Metrics、Rubric 或评测集。两种改动都要回测，评测标准本身也要接受检验。

## 几处具体的工程相似性

### Case 与 Trace 一起进入归因

个人一侧从早期的 `TestCase`、`AgentTrace`，发展到运行脚本和诊断报告。美团文章也强调通过 Trace 还原 Agent 的执行过程，再定位问题发生在哪一步。两边都把 Trace 当作失败归因的工程证据，Case 则保留触发问题的输入和预期。

### 确认的 Bad Case 会变成回归资产

个人框架支持人工确认报告，再由维护者将确认的 Bad Case 写回 regression 测试集。评测 Skill 的错判和 Gold 修正也进入独立样本集，后续用于检查评测器有没有再次犯错。

美团文章提出将 Bad Case 转成标准评测样本；白皮书进一步说明负向样本进入错题集，供后续回归。两边都让已经确认的问题成为长期回归资产，避免同类错误再次漏过。[《Agent评测漫谈》](https://tech.meituan.com/2026/08/07/Agent-Evaluation.html) [《Agent评测白皮书》](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html)

### 门禁同时看必须通过项和可按阈值判断的指标

我的项目把 `hard_gates` 和 `soft_quality` 分开。硬门禁失败会阻止候选通过；软指标先形成告警，再按策略设定的允许增量或场景阈值参与决策。这样既能守住不能退化的底线，也能对延迟、步骤数和软告警等指标做有边界的比较。详见 [README 中的版本演化说明](../../README.md)。

美团白皮书明确提到“必过集”和“挑战集”，并将离线回测用于版本变更的门控。两边都把必须守住的核心要求与其他评测目标分开处理。具体规则名称和阈值语义各有实现，不能逐项视作同一套配置。

### 评测体系本身也需要回归

两边都把评测标准和样本集当作会变化的对象。Case 归因后，若发现样本覆盖不足，就要补 Case；若发现判定标准有误，就要改 Metrics 或 Rubric。接着还要拿旧样本复查，确认新标准没有把过去正确的判断带偏。

这一步让第二条 Loop 有了具体改动对象、历史样本和回归验证。

## 差异在系统边界和实现方式

美团白皮书展示的是覆盖离线评测、在线评测与监控、Case 挖掘归因、观测基建的生产级整体视角，并列出线上评测信号、监控、用户反馈、真实样本采样和业务规则等 Case 来源。

我的 GitHub 项目定位为通用评测和受控候选演化框架。接入方提供业务 Case、规则和 Agent 适配器；项目提供 Trace 规范化、运行、归因支持、候选隔离、回归和门禁。在线数据采集与生产发布由接入方或外部流程负责，候选在项目中通过门禁后仍停留在沙箱，生产发布权属于业务方。

总结一下，两边的 Case/Trace、双 Loop、回归资产和门禁实践有很高的工程相似度，模块划分与生产接入范围则各自不同。时间线记录的是独立实践与公开方法在工程细节上的逐步收敛。
